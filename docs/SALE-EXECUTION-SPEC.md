# MarketCrate — Sale Execution Product Contract

## 15차 조건부 실행 계약 (이전 차수 제한을 대체하는 현재 범위)

제품 기본값은 SteamTradingPolicy.Blocked. 사용자가 비공식 위험을 검토하고 이번 세션을 명시적으로 선택한 경우에만 EnableUserTradingAsync가 읽기 preflight를 수행한다. Valve 허가 여부와 기술적 조건은 별개다. 단순 체크박스/ContractTest/과거설정은 계정에 바인딩된 실행권한을 만들지 않는다. QR 새시작/로그아웃/동의해제는 binding을 제거한다. 활성화는 저장하지 않는다. 같은 게임 기존 등록fee 비교가 없으면 first-bootstrap도 차단하며 미확인KRW/스택 계약을 상수로 대체하지 않는다.

모든 선택게임은 scope별 자산·fee·통화를 검증한다. SaleLineSnapshot.OrderbookDigest는 순서있는 가격/잔량/통화 SHA256이며 계정정보가 아니다. 최신호가가 달라지면 전체배치 intent 전 거부하고 VM의 이전승인을 폐기한다. 미지원 항목을 누락시키거나 자동저가로 바꾸지 않는다. reprice intent에도 optional digest를 고정하고 취소 전/반환 후 재비교한다. 구digest없는 실제사용 의도는 새검토 없이 실행 불가, 기존 합성 fixture 호환은 실제권한으로 쓰지 않는다.

CancelBatchAsync는 불변 취소대상 전체를 서버목록과 비교한 뒤 시작한다. 실행중 서버변경/부분실패는 가능하며 원자성을 주장하지 않는다. 별도 reprice의 다중항목 작업은 개별 saga이므로 전체원자성 없음. listing ID 응답이 요청전 목록에 존재하면 Unknown. 일치하는 외부후보/목록부재/스택증가만으로 자신의등록·반환을 확정하지 않는다.

한 최종 승인으로 모든 확정 단위를 intent→직렬요청→개별결과로 처리하며 추가아이템별 판매클릭 없음. Submitted/Guard대기와 Listed는 별개. 공식 모바일 앱의 여러 항목 승인은 Steam 정책에 따라 사용자가 별도로 확인해야 할 수 있다. 로컬키는 서버idempotency 보장이 아니며 JSONL은 SQLite 복구의 authority가 아니다.

## 6차 추가 계약: 승인 revision과 진단 authority

- 최종 전체 한 번 승인/immutable batch/분할 가격·수량/Guard 수동 승인/기본 live 차단 목표를 그대로 유지한다. 상세 요구 ID F01–F12는 REQUIREMENTS-TRACEABILITY에 고정한다.
- 오래된 재가격 승인은 **취소 전** 거부한다. 이미 확정 취소 proof가 있고 replacement가 미전송인 의도만 새 검토/새 승인으로 revision 가능하다. 이전 의도를 바꾸지 않고 SupersededBy를 가진 Superseded로 원자 보존, 새 intent는 CancellationKey로 원 proof를 재사용한다. 미확정 취소/스택 추정 반환/이미 전송한 replacement는 새 승인으로도 자동 재전송 불가.
- Steam schema v3 마이그레이션은 기존 v1/v2 내용/불명을 보존한다. 구 v2 앱은 v3 DB를 거부하여 Superseded 상태를 잘못 재개하지 않는다. 하위 버전 앱으로 사용 데이터 폴더를 열지 않는다.
- DiagnosticHub BatchId/OperationItemId/state transition은 진단 보조다. JSONL/ZIP 누락·실패/로그의 성공 문구로 저널 상태를 바꾸거나 재시도/예약 해제하지 않는다. 로그 실패와 판매 처리 실패를 분리한다. 실제 인과 근거 없는 ID-less 결과는 여전히 Unknown이다.

## 5차 통화·스택·관리 계약 (최신)

- 단일 최종 승인 전체 배치 목표 유지. 앱 초기값은 조회 연결 UI만 제공하며 실제 거래는 policy Blocked. 실제 Steam 로그인·등록·취소·Guard는 이번 개발에서 실행하지 않는다.
- KRW/USD의 정수 금액/wire를 구분하고 실제 wallet floor/step와 앱별 fee rate/cap을 새로 확인한다. snapshot의 통화·수령/수수료/구매자 합과 서버 profile이 다르면 첫 전송 전 거절한다. 사후 서버 반환 모순은 Unknown/후속 중단이며 이미 보낸 요청을 되돌린다는 뜻은 아니다.
- 여러 asset/context도 동일 App/hash/currency 호가를 공유한다. stack capability가 허용된 계약에서만 amount 분할, full intent와 결과별 예약을 유지한다. 실패가 확정되지 않은 수량은 해제하지 않고, 재시작/새 key로 재등록하지 않는다. 실제 스택 ID 변경은 추측하지 않는다.
- 취소 응답만으로 Cancelled 아님. 접수+목록 부재+원래 비스택 단일 자산의 반환 증거에 해당하는 원래 예약만 해제한다. 재가격 target·취소키·replacement키를 영구 보존하며 재개/이중 클릭/재시작 시 새 replacement를 중복 전송하지 않는다. 5분 경과 target은 새 검토가 필요하고 현재 가격 revision UI는 미지원이다.
- listingid 없는 후보는 메타데이터가 1건 일치해도 자신의 요청으로 자동 확정하지 않는다. 수동 도구는 증거를 보여 주며, 인과관계 증명이 없는 건 pending/Unknown 유지한다. 확정 배치 보관도 저널·증거·예약은 유지한다.

## 4차: 비활성 실험 어댑터 계약 (최신)

- 사용자 승인 범위는 비공식 어댑터 소스/합성 HTTP 검증까지다. 이번 작업에서 실계정 로그인/판매/취소/Guard를 실행하지 않는다. App은 Demo이며 필수 실등록 제품 목표가 달성되었다고 보고하지 않는다.
- 단일 승인 snapshot→실계정·현재 자산·최근 호가·정확한 수수료 재검증→로컬 intent commit→직렬 sellitem. form의 price는 buyer gross가 아니라 seller net이다. USD exact fee만 제출 가능, Demo gap 보정/원화·스택 제출은 차단한다.
- 성공 응답은 접수/공식 앱 또는 이메일 승인 대기다. listingid·종목·수량·통화·seller/fees 일치로 게시를 확인한다. 매칭 근거가 없거나 timeout/취소/403/429/형식 변경이면 Unknown 보존·후속 전송 중단·자동 retry 금지. 로컬 요청 키를 서버 idempotency 지원으로 표현하지 않는다.
- 취소 배열 응답은 Submitted까지만. 최신 목록에서 사라짐은 판매/취소 식별 증거가 아니므로 Cancelled나 재가격 허가로 바꾸지 않는다. 실제 확정 취소 이력과 새 자산 ID 매핑·재등록 saga는 미완성이다.
- 실패 retry는 기존 Mock에서만 유지하며 live는 근거 확보 전 차단한다. 실계정 GUI 연결·원화·수량 분할·정확한 거래 VWAP·다중 배치 실사용 등은 미완성으로 유지한다.

## 3차 Mock 계약 (2026-10-28, 최신)

- 매수 잔량 부족은 개별 자산의 미산정 수량 행으로 유지한다. 빈 가격은 유효하지 않으며 직접 지정한 가격이 있어야 전체 승인할 수 있다. 해당 수량은 즉시 체결 추정 불가로 표시한다.
- 개별 등록 단위의 수량/구매자 단가/Steam·게임 수수료/예상 실수령/원천·조회 시각을 분리한다. 수동 단가 변경 시 검토 합계와 우측 예상 합계를 즉시 갱신한다. 실수수료가 검증된 산식이 아니라 Demo 정책이라는 안내를 유지한다.
- 수동 가격 처리: 열린 검토에서만 유효. 전략 변경·검토 닫기·갱신은 초안을 폐기하고 새 추천가로 재구성한다. 이 규칙을 화면에 표시하며 사용자의 기존 값을 새 전략 가격인 척 재사용하지 않는다.
- 신선도는 사용자 검토/편집/명시적 확인 때 표시하고, 실제 최종 Mock 제출 시 미래/5분 만료·현재 자산/수량/통화·시세/잔량 변화를 검사한다. 자동 시세 폴링은 없다.
- 재시도는 원래 가격/수량을 다시 검토한 **확정 실패 항목만** 대상으로 한다. 시도 번호까지 불변 승인 대상으로 보고 stale/double 승인을 거절한다. 새 시도 intent를 먼저 저장하고 현재 시도 키로만 대조한다. 성공·불명·승인 대기는 재전송하지 않는다.
- 판매 관리의 가격 변경은 원래 등록의 취소 확인 이후 새 단가로 Mock 재등록한다. 부분 실패/대기/불명은 개별 보존하며 서버 원자 거래를 가정하지 않는다. 취소 확인 직후 미전송 후속 등록만 사용자 명시적 재개 가능하다.
- 취소/재가격의 불명은 외부 대조 근거가 생기기 전 계속 Unknown이다. 이번 Mock에서는 근거 없는 관리 요청을 임의로 성공/실패 확정하거나 재전송하는 버튼을 제공하지 않는다.
- 실제 최종 버튼 1회 전체 실등록 목표는 변경하지 않았다. 현재 버튼/결과/수동 fixture는 Mock이며 IntegrationBlocked를 해제하지 않는다. 허용 여부는 STEAM-INTEGRATION-FEASIBILITY를 따른다.

- 최종 승인 직전 현재 inventory의 asset/가용 수량/판매 상태와 선택 수량, 시세 통화·표본·매수 잔량을 다시 비교한다. 변경 시 모든 요청 전 검토 갱신을 요구한다. 실제 서버 검증은 아니다.

- SQLite에 intent/불변 스냅샷/항목 결과/요청 키/배치 이력을 트랜잭션으로 보존한다. 확정 스냅샷 변경과 Listed/Failed 결과의 역행은 거절한다. 단일 승인 전체 실행 및 부분 실패 계약은 유지한다.
- 같은 활성 BatchId의 재호출은 결과만 반환한다. 다른 활성 배치 요청은 거절한다. Unknown/승인 대기/전송 중/접수 상태는 새 배치를 위한 보관 해제를 막는다.
- 확정 배치를 보관한 뒤에도 이전 접수/게시/미확정 수량을 예약해 신규 배치의 중복 자산·수량을 차단한다. 명시적으로 Mock 취소 완료된 요청 키만 예약에서 제외한다. SQLite 합성 데이터 초기화는 개발용이며 실거래 운영 정책이 아니다.
- 재시작은 Mock 요청 증거와 대조만 한다. 응답 유실 이후 요청이 실제로 처리된 합성 증거가 있으면 그 결과를 복원하며, 근거가 없으면 Unknown이다. 전송 전 Ready는 자동 재개하지 않는다.
- `Mock 서버 게시 fixture 반영 후 대조`는 사용자가 합성 증거를 설정하는 별도 개발 명령이다. 모바일 승인 자동화가 아니며 Steam 네트워크를 사용하지 않는다. Submitted/AwaitingSteamGuard/Listed 구분을 유지한다.
- 배치 결과를 판매 목록으로 투영하고, 별도 취소 검토 1회로 선택 전체 Mock 취소를 실행한다. 취소 intent 후 재시작은 Unknown으로 보수 복구한다. 실제 취소/가격 변경/불명 항목의 자동 재시도는 구현하지 않는다.
- **필수 최종 목표는 여전히 실제 Steam 전체 일괄 등록이다. 이번 검증은 합성 Mock이며 LIVE_INTEGRATION_BLOCKED를 해제하지 않는다.**

> 제품 목표 문서. 이 문서는 현재 실제 거래 통합이 구현/허용되었다는 주장이 아니다.

## 사용자 여정

1. 사용자는 게임별 아이템을 선택하고 수량을 설정한다. 전체 선택과 혼합 선택 모두 가능해야 한다.
2. `최근 평균거래가` / `즉시거래가능가` 중 전략을 선택한다. 동일 아이템에 대해 구매주문 수량별 단가가 다르면 등록 단위를 분해해 상세히 보여 준다.
3. 최종 검토 창은 자산·수량·단가·수수료·실수령·예상 합계·시세 기준시각을 열거하고 최종 수정값을 수락한다.
4. **사용자가 `전체 판매등록`을 단 한 번 클릭**하면 추가 항목별 확인 없이 검토한 대상 전체에 대한 일괄 등록 처리를 시작한다. **실제 등록은 허용된 쓰기 연동이 활성화된 경우에만** 가능하며, 다른 경우 `실거래 연동 불가`를 명확히 고지한다.
5. 진행 화면은 각 주문의 전송, 수락, 모바일 승인 대기, 실제 게시 확인, 실패, 상태 불명 등을 구분하고 수동 승인 후 재조회한다.

## 핵심 설계

- `SaleBatchSnapshot`: immutable 배치/아이템/가격/수량/수수료/통화/시세 시점.
- `SaleBatchCoordinator`: 검토 확정 → 실행 잠금 → 안전한 순차 처리 → 결과 상태 기록 → 서버 결과 조정.
- `IMarketListingExecutor`: mock/blocked/permitted adapter를 분리. 비인가 비공식 쓰기 호출은 안전한 구현 수단으로 채택하지 않음.
- `SaleBatchJournal`: 민감정보를 배제한 배치·아이템별 진행 기록. 프로세스 종료/타임아웃에 대비.
- `SaleBatchViewModel`: 실행 중 이중 클릭 방지, 취소 한계 설명, 항목별 상태 및 부분 성공 안내.
- `SteamGuardPending`: 공식 모바일 앱에서 사용자 직접 승인 필요. 승인 전 판매 완료 아님.

- 이중 클릭, 네트워크 타임아웃, 요청 응답 상실, 앱 강제종료·재시작에서 중복 등록이 발생하지 않도록 보수적으로 중단·대조하는지.

## 릴리스 완료 판정

- `UI/MOCK_READY`: 검토·일괄 오케스트레이터·진행/결과 화면까지 Mock으로 동작.
- `LIVE_INTEGRATION_BLOCKED`: Steam 허용 근거 또는 권한이 없어 실제 판매 불가. 안전상의 이유를 제품에 표시.
- `LIVE_READY`: 허용된 실제 등록 경로가 검증되었고, 명시적 사용자 설정 후 실제 등록·승인 대기·재조회가 정확히 작동하는 경우만. 실제 사용자 계정에서의 테스트는 사용자의 별도 명시적 요청으로만 진행.

## 최초 Mock 구현 계약 (2026-10-28)
- ViewModel의 `Submit` 최종 명령 1회→모든 검토 행을 `ImmutableArray`로 복사해 스냅샷 고정→coordinator 순차 처리. 명령 잠금/프로세스 내 semaphore/프로세스 간 journal 파일 lease로 중복 진입을 제한한다.
- 스냅샷은 BatchId/AccountReference(고정 합성 ID)/FinalizedAt 및 LineId/개별 AssetKey/marketable·tradable·stackable·수량/통화/단위 수수료 견적/MarketTime을 보존한다. 검토의 사용자 가격 수정값을 사용한다.
- 현재 KRW만 허용, 5분 만료, 미래 시세·중복 LineId·자산 총량 초과·서로 모순되는 동일 자산·보류/비판매·잘못된 수수료 차단. 서버 잔고와 대조한 실제 자산 검증은 아니다.
- 동일 market hash 자산의 구매주문 깊이를 공유해 검토 시 잔량을 차감한다. 수량 부족이면 검토 전체를 중단하고 수량/전략 변경을 안내한다. 자동으로 가격을 만들어 나머지를 채우지 않는다.
- 요청 키는 `BatchId:LineId`. `Ready` 저널과 항목별 `Submitting`을 디스크에 기록한 이후에만 Mock executor를 호출한다. 타임아웃/응답 불명은 Unknown으로 기록하고 후속 행 전송을 멈춘다.
- 일부 `Failed`는 다른 확정 결과를 유지한다. `Submitted`/`AwaitingSteamGuard`는 `Listed`와 다르다. 앱의 mock executor는 게시/승인 증거를 만들지 않는다.
- 복구는 Submitting/Unknown/Submitted/AwaitingSteamGuard만 대조한다. Mock 서버 증거가 없으므로 Unknown으로 남긴다. Ready를 포함해 자동 재제출하지 않는다. 취소 후 명시적 항목별 안전 재시도·거절/만료 상세 흐름은 미구현이다.
- 스키마 v1 단일 Mock 배치 저널은 합성 ID만 기록한다. 테스트는 저장·재시작·파일 lease를 검증하지만 OS 강제 전원 차단·실제 네트워크/계정·장시간 안정성을 인증하지 않는다.
- **현재 UI의 `Mock 배치 전체 실행`은 실제 등록이 아니다.** 최종 제품의 `전체 판매등록` 단일 승인 계약은 그대로 남아 있으며 허용된 실연동 확보 전 LIVE_INTEGRATION_BLOCKED.
