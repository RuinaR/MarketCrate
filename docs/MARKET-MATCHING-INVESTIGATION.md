# 등록됐지만 같은 표시 호가에 체결되지 않는 경우

확인일: 2026-10-31 KST. 사용자0.20.14 정상 동작·판매등록 성공 보고와 첨부 화면에 근거한 조사다. Codex는 인증된 계정 조회/판매/취소/재가격/Guard를 실행하지 않았다.

## 관측과 판정

- TBH/App3678970, Contaminated Soulstone - Torment의 사용자 판매 항목이 화면에 나타난다. 단가는70원, 괄호 금액은50원으로 보인다. 아래 주문장에는 최저 판매70원18개, 최고 구매70원416개가 표시된다.
- 이 보고는 해당 사용자·항목의 실제 등록/게시 관측 증거다. 가격표의70원 동등만으로 실제 매칭 가능한 원통화 금액까지 동일하거나 체결이 보장된다고 판단하지 않는다. 전체 게임/통화/스택/장기 복구/모바일 승인 경로의 실증으로 확대하지 않는다.
- 구매자 결제액70원과 판매자 수령액50원을 비교해야 한다. 두 금액의20원 차이는 이 화면에서 수수료 총액에 해당하며, 구매주문70원과 판매자 수령50원을 서로 다른 판매가격이라고 해석하지 않는다. 구체 Steam/게임별 배분은 당시 실제 계약이 필요하다.

## 공식 자료에서 확인한 사항

Steam [Community Market FAQ](https://help.steampowered.com/en/faqs/view/61F0-72B7-9A18-C70B): 판매자는 자기 지갑 통화로 등록하고 구매자는 자기 지갑 통화로 가격을 본다. 교차 통화는 Steam의 일별 갱신 환율을 적용한다. 구매주문은 조건을 충족하는 저가 판매를 찾으며, 여러 신규 판매 매칭 후보 구매주문이 있으면 오래된 적격 구매주문을 선택한다. 잔고/구매 처리/계정 문제 등으로 구매주문이 취소될 수 있다.

따라서 ‘가장 높은 표시 구매주문부터 수량 배분’은 가격 제안이며 실제 상대방/체결 순서를 지정하는 서버 명령이 아니다. 단순히 앞에 판매자가 있다는 사실만으로 지속적인 crossed display를 전부 설명할 수도 없다.

공식 [economy_common.js](https://community.fastly.steamstatic.com/public/javascript/economy_common.js)를 새로 받아 확인했다. SHA256 84429D06A9EF8C250AC567F9FEDC9FB155D23CEB7442C92A19B815840C102784. ToValidMarketPrice는 실제 wallet_market_minimum/wallet_currency_increment로 금액을 보정하고, CalculateFee/GetTotalWithFees는 수수료·구매자 총액을 계산한다. 이 파일의 환산 함수에는 floor/ceil 및 역환산 보정이 있다. 클라이언트 함수가 서버 전체 매칭 알고리즘을 공개한다는 의미는 아니다.

## 코드와 비교 프로젝트 대조

- MarketCrate Money는 KRW 정수 원과 Steam wire 단위를 분리하고 KRW wire 변환은 정수×100/정확 나눗셈이다. 표현 불가능한 단위를 조용히 반올림하지 않는다.
- SteamContract.OrderBook은 현재 통화의 rgCompactBuyOrders 가격/수량을 읽고, SalePlanner는 같은 상품의 잔량을 공유한다. SteamReviewRow는 해당 호가 이하에서 수수료/증분으로 도달 가능한 구매자 총액을 계산한다(FromBuyer(..., false)). 승인된 값보다 자동으로 낮은 금액을 전송하지 않는다.
- 이 경로는 외국 구매자의 원통화·개별 주문의 실제 체결 적격 여부를 보유하지 않는다. 현재 화면만으로 부동소수점 오차나100배 단위 오류가 원인이라는 증거는 없다. 실제 예상70/실제 게시70은 적어도 이 항목에서 눈에 보이는 등록가 불일치는 아니라는 증거다.
- MIT [SteamMarketHelper e186d51](https://github.com/federicogiorgi/SteamMarketHelper/blob/e186d51efb742ddfb527d2ccb248c64fcee9c976/steam-market-helper.user.js)의 buildOrderBook/targetPriceForNewListing/sellerPriceForTarget를 실제 소스로 확인했다. 최저 경쟁 판매보다 낮게 제안하되 최고 구매주문/최저 판매의 경계를 고려하고 수수료 역산 후 실제 구매자 총액을 다시 확인한다. 경계가 같으면 같은 호가가 나올 수 있다. 환율·서버 매칭을 강제하는 API가 아니므로 무조건 복사하면 즉시 체결된다는 근거가 아니다. USD cents 기반 보정값1을 KRW1원으로 그대로 도입하지 않았다. 새 구현 코드 복사0.

## 원인 가설과 확정 한계

우선 확인할 가설은 교차 통화 환산·표시/가격 증분 보정으로 서로 다른 체결 조건이 같은70원으로 보이는 경우다. 이 현상과 잘 맞지만, 외국 주문의 원통화/환율/적격 여부를 확보하지 못했으므로 이번 항목의 확정 원인이라고 표시하지 않는다.

다음 후보는 주문장/화면의 갱신 시점 차이, 승인 대기 시간 동안 주문장 변경, 구매자의 잔고/처리 문제다. 순수한 등록 실패·Guard 미승인과 이미 실제 게시됐으나 미체결인 상태를 구분한다. 현재 공개 상품 페이지의 다른 통화/다른 시점 수치를 사용자 화면과 직접 비교해 환율 증거로 삼지 않았다.

## 현재 가능한 방법

1. 공식 장터를 직접 한 번 새로고침해 해당 항목이 실제 활성 판매 중인지와 최신 매수 호가를 확인한다. 그대로 가격을 유지해 기다리는 선택도 가능하다. 이미 게시된 항목을 새 등록 버튼으로 중복 제출하지 않는다.
2. 빠른 체결을 우선하고 더 적은 실수령을 받아들이는 경우에만 기존 판매 취소 확인 → 새 검토 → 현재 호가보다 **서버가 허용하는 한 단계 낮은 실제 구매자 총액**을 직접 승인한다. 통화 증분/최소 수수료 때문에70→69원이 불가능할 수 있다.
3. 조건부 예: 실제 계약이10원 증분이고70원 구매자/50원 수령에서 각각 수수료10원+10원이라면 다음 가격이60원 구매자/40원 수령일 수 있다. 이는 현재 계정의 증분을 확정한 값이 아니며, 수령액이50→40으로20% 줄어드는 변경이다. 공식 판매 화면과 새 검토의 실제 계산으로 확인해야 한다. 한 단계 하향도 실제 체결 보장은 아니다.
4. 반복 자동 취소/재등록·자동 가격 인하·원화 소수/외화 위장 전송은 하지 않는다. 취소/반환 불명은 기존 보호를 유지한다.

향후 제품 개선은 기본 ‘호가 유지’와 명시적 ‘체결 우선: 한 유효 단계 하향’을 구분하는 방향이다. 도달 가능한 실제 구매자 가격과 순수령 감소액/비율, 최소 실수령을 검토에 표시하고 새 단일 승인을 받아야 한다. 기존 승인 가격을 변경하는 자동 폴백은 허용하지 않는다. 이번 요청은 원인/방법 조사이므로 가격 정책·앱 바이너리를 임의 변경하지 않았다.

확정 분석에 유용한 추가 증거는 사용자 명시적 갱신에서 얻은 통화, 수수료 모드, 최소/증분, 최상단 raw wire와 표시 가격, 실제 등록의 seller/fee/buyer, 조회 시각·페이지 완전성이다. 허용된 값만 정제 요약하고 쿠키·계정 ID·원본 응답·인증정보는 수집하지 않는다. amtMaxBuyOrder와 첫 compact level이 함께 있으면 그 일치도 점검하되 차이를 임의로 환산/보정해 제출하지 않는다.
